# 算子之外，聊聊 PostgreSQL 的设计

最近看到一份 Oracle 执行计划的算子清单，列了两百多条操作和它们的变体，从表扫描、索引访问，到连接、聚合、分区、并行执行，几乎把优化器能选的物理路径铺了一遍。

这些算子确实是 Oracle 攒了多年的家底。SQL 的形态和数据分布千差万别，只有准备了足够多的执行路径，优化器才有机会挑到合适的那个；而这些名字背后，往往还对应着被大量业务反复验证过的实现。

不过沿着这份清单去看 PostgreSQL，我注意到的是另一件事。

Oracle 很早就有 `INDEX SKIP SCAN`，专门解决复合索引缺少前导列条件时的访问问题。PostgreSQL 直到 18 才正式引入对应的 B-tree Skip Scan 优化，可打开执行计划，却找不到一个新的 `Index Skip Scan` 节点。它仍然显示为熟悉的 `Index Scan` 或 `Index Only Scan`。

节点的名字没有增加，背后的执行能力却实实在在地变强了。

这倒不是说 PostgreSQL 不需要丰富的物理路径，而是两者组织执行能力的方式不太一样。Oracle 习惯把具体的执行策略直接写进计划节点的名字里，PostgreSQL 则有相当一部分能力，藏在已有的执行节点、访问方法和扩展接口下面。

当然，Oracle 的计划节点内部同样有大量没显示出来的实现细节，PostgreSQL 也会在需要的时候引入新节点。差别不在“算子多”还是“算子少”。

我更想弄清楚的是：**一种新的执行能力，究竟应该放在数据库的哪一层？又该怎样融进原有体系，而不是每次都重新造一套实现？**

PG 18 的 Skip Scan，从最初的提案到最终合入，恰好是个不错的观察窗口。

这篇里的不少想法，是在和做产品的“小白老王”大佬闲聊时慢慢成形的。我平时更关心 B-tree 内部怎么实现，他更关心这些能力最后怎么落到产品上、客户那边看不看得明白。两种视角来回碰几次，原本模糊的取舍就清楚了一些。

## 一、同样是 Index Scan，背后干的活可能不一样

先看一个很小的例子。

Oracle 用 B-tree 索引取数据时，执行计划里经常能看到这样的结构：

```text
TABLE ACCESS BY INDEX ROWID
  INDEX RANGE SCAN
```

索引查找和按 ROWID 回表被拆成了两步。DBA 一眼就能看出，数据库先通过索引定位到记录，再去表里取数据。

PostgreSQL 通常把这两步合在一个 `Index Scan` 节点里：执行器调用索引访问方法拿到 TID，再去 Heap 里取记录，中间还要做可见性检查。

反过来也一样。PostgreSQL 的哈希连接一般会显示成独立的 `Hash` 和 `Hash Join` 两个节点，Oracle 的 `HASH JOIN` 则已经把建哈希表的过程包含进去了。

两边完成的物理动作其实差不多，只是计划树的拆法不同。

这里有个容易被忽略的事实：**执行计划节点，并不是数据库物理算法唯一的抽象层次。**

在 PostgreSQL 里，一次查询大致要经过三层。

| 层次 | 负责什么 | 相关实现 |
| --- | --- | --- |
| Optimizer Path | 构造候选路径，估计成本，做出选择 | `IndexPath`、`cost_index()` |
| Executor Node | 驱动执行，向上层返回元组 | `IndexScan`、`IndexOnlyScan` |
| Index Access Method | 处理索引内部的搜索与遍历 | `btgettuple()`、`btgetbitmap()` |

优化器判断该不该走索引，执行节点组织取出数据的过程，具体怎么在 B-tree 里找到下一条匹配记录，则是索引访问方法的事。

这层划分本来就存在。PG 18 的 Skip Scan 并没有改动上面的执行模型，只是在 B-tree 已有的访问机制里多了一种搜索方式。想清楚这一点，再看它的实现就容易多了。

## 二、Skip Scan 给复合索引多开了一条路

假设有一张订单表，上面建了这样一个复合索引：

```sql
CREATE INDEX orders_status_customer_idx
    ON orders (status, customer_id);
```

`status` 只有少数几个取值，`customer_id` 的取值却很多。

现在要查某个客户的全部订单：

```sql
SELECT *
FROM orders
WHERE customer_id = 1024;
```

问题在于，这个查询没有给前导列 `status` 提供条件。

B-tree 按 `(status, customer_id)` 的顺序组织键值，先按 `status` 排，同一段 `status` 里再按 `customer_id` 排。客户 1024 的记录因此会散落在不同状态对应的索引区间里。

在 PG 18 之前，这也不意味着索引完全用不上。`customer_id = 1024` 依然可以在索引内部判断，筛掉一部分不必回表的记录。但缺了前导列约束，扫描没法直接收缩到一个足够小的连续范围。

Skip Scan 改的正是这一点。

假设 `status` 只有 0、1、2 三个非 NULL 取值，可以把它理解成索引内部依次处理：

```sql
status = 0 AND customer_id = 1024
status = 1 AND customer_id = 1024
status = 2 AND customer_id = 1024
```

这只是方便理解的示意。PG 不会先查出所有不同的 `status`，再把 SQL 改写成几个分支。真正的做法是扫描过程中动态生成前导列的等值约束，跟着索引里的实际数据往前走。

于是，原本要趟过一大片无关索引区域的查询，现在可以反复定位到几个小得多的候选范围。

多次定位当然也有成本。前导列的不同值一多，每个取值都要重新搜一次，未必比顺着索引连续读更划算。Skip Scan 更适合前导列基数低、后续列选择性高的场景。

这里还有个值得注意的变化。

以前碰到这类查询，我们通常会考虑单独建一个 `(customer_id)` 索引，或者重新掂量复合索引的列顺序。Skip Scan 替代不了正常的索引设计，但它确实让已有的复合索引能服务更多查询。

对某些混合负载来说，甚至可以重新考虑要不要多维护一个单列索引。索引带来的不只是查询收益，还有写入、维护和存储的成本。

这明显是一项新的执行能力。但在 PG 18 里，它依然只是 B-tree 索引扫描的一部分。

## 三、为什么不新加一个 Skip Scan 节点

2024 年 6 月，Peter Geoghegan 把 [Adding skip scan to nbtree](https://www.postgresql.org/message-id/CAH2-Wzmn1YsLzOGgjAQZdn1STSG_y8qP__vggTaPAYXJP%2BG4bw@mail.gmail.com) 的原型补丁发到了 pgsql-hackers。

这项工作接在 PostgreSQL 17 对 B-tree 数组条件扫描的改进后面。之前的版本已经能更有效地处理 `IN`、`ANY` 这类带多个搜索值的条件，Skip Scan 则在这套机制上引入了一个按需产生候选值的 *skip array*。

Peter 在提案里特意强调，新实现没有改变 B-tree 与执行器之间原有的接口约定，也不需要优化器生成一条独立的 Skip Scan 路径。

这么设计，不只是为了少维护一个节点。

邮件里他举了一种很有代表性的数据分布：某个前导列上，90% 的索引项集中在三个取值里，剩下 10% 的索引项几乎各不相同。

对前 90% 的数据来说，跳过大片无关的索引区域很划算；到了后面 10%，如果每个键值都要重新发起一次搜索，成本可能比直接读相邻页面还高。

也就是说，同一次索引扫描里，可能这一段适合跳跃，下一段又适合连续读取。

如果在规划阶段就把普通索引扫描和 Skip Scan 做成两条互斥的路径，优化器就得提前决定整段扫描该用哪种策略。

可优化器手里主要是统计信息和成本估计。真正知道当前页面里有什么键值、是否已经越过匹配范围、下一段索引值不值得重新定位的，是运行时的 B-tree。

让 B-tree 根据当前扫描状态决定什么时候重新定位、什么时候接着顺序读，等于把这类局部决策留给了信息更充分的一层。

最终实现正是沿着这条思路展开的。

PG 18 的 `create_index_path()` 仍然通过 `IndexPath` 描述索引扫描的候选路径，没有新增 `SkipScanPath`。B-tree 则在扫描键的预处理和推进过程中，加入了动态生成和维护 skip array 的机制。

优化器当然也不是完全不管 Skip Scan。`btcostestimate()` 就得把可能的重复搜索、前导列不同值的数量和索引扫描成本都算进去，否则原本不划算的复合索引扫描，还是可能输给顺序扫描。

两层分工依然清楚：优化器比较不同访问路径的整体代价，B-tree 在被选中的那次扫描内部，利用运行时的局部信息安排导航。

这么设计还有个附带的好处。Skip Scan 走的还是原来的索引访问接口，所以能继续参与 PostgreSQL 已有的计划组合，普通索引扫描、仅索引扫描、生成位图的索引扫描都能用上，不必为每种上层用法重新提供一套执行机制。

这背后其实是个挺朴素的工程习惯：把优化放在最适合处理它的层次，让新能力尽可能复用已有机制。

## 四、新能力进入内核，也要照顾原有负载

Skip Scan 的开发过程里，还有一段讨论特别值得看。

最初的提案中，Peter 为了展示这项优化，参考了 1995 年一篇关于多维 B-tree 访问的研究论文，重建了其中一组测试数据。表大约 51GB，索引大约 25GB，查询同时涉及缺失的前导列条件、日期范围和多个 `IN` 条件。

在他当时的测试环境里，旧实现完整扫一遍索引要 32 秒左右，打上补丁后不到 52 毫秒，差了大约 630 倍。

数字确实惊人，但 Peter 自己紧接着就提醒，这个倍数其实没有太大意义，因为原来的完整索引扫描本来就是个非常差的基线。倍数堆得再高，也证明不了什么。

他真正想说明的是：新的访问机制，让一类原本不太合理的大型复合索引设计开始变得可行了。

这个判断比单纯展示加速倍数有价值得多。它关心的是数据库能不能处理过去处理不好的场景，而不是某个基准测试跑快了多少倍。

真正困难的另一面，是新机制可能拖慢原本跑得好好的查询。

2024 年 11 月，Masahiro Ikeda 在补丁评审中报告过一个性能回退的案例。两份计划都是 `Index Only Scan`，都只有一次 `Index Searches`，访问的 Buffer 数量也相同，但启用相关跳跃扫描机制后，执行时间从 17 毫秒左右涨到了 66 毫秒左右。

原因并不难理解。即使这次扫描最终没跳过几个索引页面，新的扫描键、候选值和状态维护照样要消耗 CPU。

减少 I/O 的机会没有兑现，额外的 CPU 开销却已经付了。

数据库里很多优化都卡在这里：让一部分场景变快并不困难，困难的是不给用不上这项优化的场景添成本。

后续的配套补丁处理的就是这件事。

2025 年 4 月合入的 [`startikey` 优化](https://www.postgresql.org/message-id/E1u0juY-002ezY-2Q@gemulon.postgresql.org)，替换了之前的 `prechecked` 和 `firstmatch` 机制。它利用当前 B-tree 页面已经确定满足的条件减少不必要的键比较，并在合适的时候暂停页内的数组状态维护。

这样一来，扫描在不适合跳跃的区段可以尽量贴近原来连续读取的开销，进到别的区段再保留继续跳跃的机会。

这项处理并没有消掉所有回退，提交说明里仍然记着复杂范围条件、极短扫描等场景下的限制。但已经能看出，社区关心的不只是新算法在目标场景下能跑多快，还包括它进入常用扫描路径之后，对已有查询意味着什么。

这大概就是实现一个独立算法，和把算法集成进成熟数据库之间的区别。

独立算法可以只挑最适合自己的输入；内核里的优化则要面对真实的数据分布、统计信息的误差和大量已有的负载，必须在收益与额外开销之间找到那个能接受的平衡点。

## 五、节点没变，执行过程仍然要能看见

把 Skip Scan 放进 B-tree 内部，也带来一个问题：DBA 怎么知道这次索引扫描到底跳没跳？

Oracle 把 `INDEX SKIP SCAN` 明明白白写在执行计划里，这一点很有价值。看到这个名称，就知道当前用的是什么访问策略，可以顺着前导列的选择性和重复定位的成本继续往下分析。

PostgreSQL 没有新增对应的节点，就得另想办法把内部行为露出来。

开发 Skip Scan 期间，社区专门讨论过怎么在 `EXPLAIN ANALYZE` 里展示底层的索引搜索次数，最后引入了 `Index Searches` 统计。

PG 18 的官方文档里有个例子：

```sql
SELECT four, unique1
FROM tenk1
WHERE four BETWEEN 1 AND 3
  AND unique1 = 42;
```

索引建在 `(four, unique1)` 上，计划里能看到：

```text
Index Only Scan using tenk1_four_unique1_idx on tenk1
  Index Cond: ((four >= 1) AND
               (four <= 3) AND
               (unique1 = 42))
  Heap Fetches: 0
  Index Searches: 3
```

这次扫描发起了三次索引搜索，分别去定位 `four = 1`、`four = 2` 和 `four = 3` 对应的候选范围。

节点仍然是 `Index Only Scan`，但 `Index Searches` 让人看见它在里面搜了几趟。

当然，这个指标不能直接等同于跳跃次数。`IN`、`ANY` 这类数组条件，以及父节点触发的重复扫描，同样可能产生多次索引搜索。真要分析，还得结合索引条件、`loops`、Buffer 访问和执行耗时一起看。

2024 年那次讨论里，还有人建议把 `Index Searches` 和 `pg_stat_all_indexes.idx_scan` 的命名统一起来，省得大家混淆。但这么改会动到既有统计接口的兼容性，名字最后还是留了下来。

这个细节挺有意思。加一项执行统计看着是小事，照样得掂量使用者的习惯和接口的稳定性。

复用旧节点能降低执行层面的复杂度，代价不能是可观测性。

Oracle 用更明确的计划名称来传达访问策略，PG 则在保留原有节点抽象的同时，一点点补上运行时的细节。两种做法各有各的道理。对实际用的人来说，要紧的是能判断数据库到底干了多少活，收益从哪儿来，额外开销又花在哪一步。

## 六、什么时候加节点，什么时候扩展已有能力

看到这儿，可能会以为 PostgreSQL 的倾向是尽量不加执行节点。

其实不是。

PG 13 加了 `Incremental Sort`，利用输入已经满足的排序前缀，避免把全部数据重新排一遍。

PG 14 又加了 `Memoize`，缓存参数化 Nested Loop 内层扫描的结果，参数重复出现时就不必重算。

这两项能力用的都是独立执行节点。

原因在于，它们本身就带着需要单独管理的执行状态。

`Incremental Sort` 要识别输入里已经排好序的分组，管理组内的排序和输出；`Memoize` 则要维护缓存键、缓存条目、命中状态，还有淘汰和重扫的逻辑。

放进独立节点，这些机制才能和其他执行节点自由组合，不必把缓存或增量排序的逻辑分别塞进好几种上层算子。

Skip Scan 的情况不太一样。它没有改变索引扫描向上层返回元组的基本方式，改的主要是 B-tree 在内部怎么导航、什么时候跳过无关的索引区域。

既然已有的索引访问接口接得住这项能力，就没有必要为了在计划里显示一种新策略而单独加个节点。

我觉得这才是 PG 在这里值得细看的地方：它不刻意追求节点少，而是看一项能力的职责和状态边界落在哪里，再决定该放在哪一层。

同样的思路也体现在扩展机制上。

PG 18 的 Skip Scan 给 B-tree 加了可选的 `skipsupport` 支持函数，让操作符类可以提供针对具体数据类型、在索引键空间里推进候选值的方法。

这里的 operator class 指的是索引操作符类，不是执行计划里的算子。通用的 B-tree 负责组织扫描，类型相关的知识由支持函数补上。即使没有提供 `skipsupport`，核心也还有回退策略能跑 Skip Scan。

再往上，PostgreSQL 通过 Index Access Method 接口允许接入不同的索引实现。扩展可以提供自己的索引构建、扫描、维护和成本估计逻辑。

如果一种新策略需要直接参与优化器的路径选择，还可以用 `CustomPath` 和 `CustomScan`：扩展给出候选路径及其成本，被优化器选中后转换为计划，再由自定义的执行回调完成工作。

这些接口当然不意味着新算法能零成本进入生产环境。扩展照样要处理结果正确性、成本估计、重扫、并行安全，`CustomScan` 这类设施也有明确的适用边界。

但它们确实给了数据库一项重要的能力：不必把每一种专用执行策略都提前写死在核心里。新的需求可以根据自身特点，在类型、索引访问方法、执行节点这些不同层次上找到接入位置，并尽可能复用已有的规划和执行机制。

从这个角度看，PostgreSQL 的可扩展性不只是能加函数、加类型、加插件，更在于它给新能力留了参与原有执行体系的位置。

## 七、兼容性和内核演进并不矛盾

再回到那份 Oracle 算子清单。

对于以 Oracle 为主要兼容目标的国产数据库来说，补齐对应的 SQL 语义、执行策略和计划表达，都是很有价值的工作。

一方面，物理路径越丰富，优化器手里的选择越多；另一方面，沿用 Oracle 的 SQL 写法和看计划的习惯，也能降低应用迁移和后续调优的成本。

原有业务 SQL 少改一点，DBA 的调优经验多留一点，迁移的风险就有机会降一点。这些能力值得做，也需要长期积累。

但如果底层用的是 PostgreSQL，兼容工作同样能和 PG 自身的设计演进互相补充。

应用迁移解决的是已有业务怎么平稳搬进新系统；访问方法、优化器和执行器的持续改进，则决定了这些业务在新系统里还能得到多少性能提升和新能力。

Skip Scan 就是个例子。它不依赖任何 Oracle 特有的 SQL 语法，SQL 不用改，索引不用改，只是底层 B-tree 多了一种有效的搜索方式，过去不划算的访问路径就可能变得值得选。

所以兼容性建设和内核演进完全可以一起推进。前者保护用户已经攒下的应用和经验，后者让数据库继续长出新的执行选择。

## 算子之外

Oracle 那份算子清单，体现的是多年真实业务磨出来的执行能力。每多一条有价值的物理路径，优化器在某类场景下就多一个更合适的选择。

PostgreSQL 的 Skip Scan 展示的是另一种积累方式。

它没有新增执行节点，却让已有的 B-tree 扫描能处理更多查询；没有为普通扫描和跳跃扫描各维护一套执行体系，而是利用访问方法掌握的局部信息，在运行时安排更合适的走法；同时又补上成本估计、回退控制和执行统计，让这项能力真正进入原有体系，并且以后还能继续维护。

PG 的其他执行节点和扩展机制里，也能看到类似的取舍：需要独立状态和执行逻辑时加节点，现有抽象够用时就加强原机制，适合外部实现的则尽可能留出接口。

算子清单能告诉我们，一款数据库积累了多少种执行办法。但清单之外还有另一层信息：这些办法靠什么机制工作，怎么参与优化器选择，又解决了哪些过去处理不好的场景。

数据库的很多改进，最后都会体现为执行效率的提升。但在这之前，它们往往先发生在架构边界、算法选择和工程取舍里。

有些会变成执行计划里的一个新名字，有些则一直待在已有节点下面。
